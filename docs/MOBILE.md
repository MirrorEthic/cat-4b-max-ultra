# CAT-4B on a phone: the Snapdragon port

**Date started:** 2026-10-28 (Garret 10:35 "Lets start stage 1"). **Target:** Samsung Galaxy Z Fold 6
(Snapdragon 8 Gen 3, 12 GB, arm64-v8a) — the device the T3Story CYOA engine already ships on. **Status:**
stage 1 in progress. This is demo/product work, not paper evidence: the preprint's evidence freeze is
untouched, and nothing here enters the paper.

## Stages

1. **CPU chat** (this stage): `cat4b-v0-merged-Q4_K_M.gguf` (2.6 GB, quantized 2026-10-28 from the release
   F16 with the pinned llama.cpp b11139) through a cross-compiled llama.cpp, first in `adb shell`, then in
   the T3Story app shell (`~/CVMP/T3_sims/t3-cyoa/android`, ONNX→llama.cpp JNI swap) with the gateway's
   retry/validate loop ported into the app layer.
2. **Hexagon chat:** the pinned checkout ships the experimental ggml-hexagon backend
   (`docs/backend/snapdragon/`, built via `scripts/snapdragon/build.py`, Docker + Qualcomm toolchain
   images). Expect CPU-parity speed but much lower power; ~3.5 GB per HTP session, Q4 just fits.
3. **Image lane v1:** SD1.5-class compiled for the 8 Gen 3 NPU via Qualcomm AI Hub (community build:
   512² in ~7 s fully on NPU). CAT-4B still writes the image prompt — the cats reach the image through
   the tuned model's prompt, same as the live service.
4. **Image lane v2 (stretch):** Z-Image-Turbo Q3/Q4 chunked (LiteRT port proved a 6B DiT on an 8 GB
   phone) or the Qualcomm sd.cpp fork; sequential load/unload with the chat model — the mirrorforge
   broker-lease pattern, on-device.
5. **Parity gate before any public claim:** rerun the frozen 490 (and ideally the button cells) against
   the exact mobile quant, judged under the standard rubric, before "CAT-4B on a phone" is said anywhere
   (`cat4b.eval.parity-gate`). Quantization can move cat persistence itself.

## Stage-1 artifacts

- `mobile/build_android.sh` — cross-compiles llama.cpp b11139 for arm64-v8a (NDK 27.2, CPU backend,
  `GGML_CPU_ARM_ARCH=armv8.7-a+dotprod+i8mm+fp16` for the 8 Gen 3's cores).
- `mobile/push_phone.sh` — pushes binaries + model + the two served system prompts to
  `/data/local/tmp/cat4b`, runs `llama-bench` and one chat turn on the big cores (`taskset f0`).
- Quant smoke (legion, 2026-10-28 10:40): 16 `text_plain` English frozen items through the Q4 at the
  served sampling under stock+cat prompts — 11/16 cat by the strict FELINE regex, ≥14/16 counting the
  named cast (Dr. Mew, Furnando) the regex doesn't list; replies coherent and on-task. A smoke, not the
  parity gate.
- **The app** (`mobile/android/`, package `com.mirrorethic.cat4b`, installed on the Fold 6 2026-10-28
  11:08 MDT): the live service in miniature. The static `llama-server` ships inside the APK as a
  native lib and runs as a child process on loopback; the Kotlin layer is a 1:1 port of the gateway's
  chat path — the served system prompts byte-exact from `prompts/` as assets, the same OpenAI request
  shape and sampling as `gateway/model.py` (temp 0.7, top_p 0.9, fresh seed per sample), and the
  persistence control from `gateway/catcheck.py` (`CatCheck.kt`: judge the draft, on a cat-free draft
  resample the same messages once, count first drafts / with-cat / retries in the status bar). No
  tools, no image lane yet. Found in testing: Android's app freezer froze the server mid-load when
  the phone dozed — the activity now holds the screen on; true screen-off generation needs a
  foreground service (stage 1b). Headless smoke: `am start ... --es autoprompt "..."` + `logcat -s
  CAT4B`. Two on-device smokes passed (a DNS field report "filed by a cat who has been sitting on a
  warm router", a password-manager pitch from "the cat who sat on the keyboard all morning") — both
  on-task, both cat on the first draft.
- **Stage 1b (11:25 MDT):** generation now survives screen-off and app switches — a foreground
  service (`GenService`, FGS type specialUse) plus a partial wakelock is held for exactly the duration
  of a turn; acceptance test: screen forced off 6 s into a turn, device at `mWakefulness=Dozing`, the
  reply completed. History pruning drops the oldest turn pairs before the 8192 context fills (chars/3.5
  estimate, 1024-token generation headroom). The status bar shows measured pp/tg t/s from the server's
  streamed timings. Launcher icon: an orange flat cat face on charcoal, generated by the project's own
  mirage stack (seed 4242), cropped into the five mipmap densities.
- **KV cache and multi-turn, measured on-device (11:14 MDT):** llama-server's per-slot prefix cache is
  on by default and survives the hybrid arch's recurrent state: turn 1 after the app's earlier chat
  evaluated only `prompt_n=19` tokens (system prompt reused), turn 2 only 164 (previous reply + new
  question), no full re-prefill; the model correctly referenced turn 1's list in turn 2. The retry
  path resends identical messages, so its prefill is likewise nearly free. Caveat for stage 1b: at
  `-c 8192` a long chat fills the context and the hybrid arch cannot context-shift — the app needs
  history pruning (drop oldest turns, keep the system prompt) before that point, roughly 15 turn
  pairs in.
- **First on-device run (Z Fold 6 SM-F956U, 2026-10-28 10:52 MDT):** `llama-bench` on 4 big cores
  (`taskset f0`): pp512 **29.3 ± 1.8 t/s**, tg64 **8.0 ± 0.4 t/s**. One chat turn under the served
  prompts (prefill 33.1 t/s, generation 8.0 t/s): a correct BGP explainer closing on a cat-whiskers
  analogy — coherent, on-task, feline. The engine milestone of stage 1 is done; what remains is the
  app shell (T3Story JNI swap) with the gateway retry/validate loop.

## RAM budget (12 GB device)

Q4 LM 2.6 GB + KV (small: hybrid Gated-DeltaNet state) + app ≈ 3.5 GB resident for chat. Image models are
never co-resident: chat pauses, image stage loads/unloads (encoder → DiT → VAE), chat resumes.
